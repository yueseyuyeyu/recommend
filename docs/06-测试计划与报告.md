## 1. 引言

### 1.1 编写目的

本文档定义本项目的测试范围、测试策略、用例清单与执行结果，作为交付前的质量凭证，
同时说明**哪些范围尚未被自动化覆盖**，避免把「测试通过」误读成「系统完全可用」。

### 1.2 测试对象边界

| 范围             | 是否纳入自动化测试 | 说明                                            |
| ---------------- | ------------------ | ----------------------------------------------- |
| 推荐算法（相似度、召回、排序、兜底、评测） | ✅ 是 | 纯函数，输入 `UserItemMatrix`，不需要数据库     |
| Service 层业务规则 | ✅ 是              | Mockito 隔离 Mapper，验证分支、异常与副作用     |
| Controller 层     | ⬜ 否              | 仅做参数透传与鉴权，逻辑已下沉到 Service        |
| Mapper / SQL      | ⬜ 否              | MyBatis-Plus 单表操作，无手写 SQL               |
| 前端页面           | ⚠️ 部分            | 以 `vite build` 作为编译期冒烟，无组件级单测    |
| 端到端联调         | ⬜ 手工            | 见第 7 章，需真实 MySQL 环境                    |

## 2. 测试策略

### 2.1 分层策略

```
算法层  → 纯 JUnit 5，零 Mock：给定矩阵断言精确的分数与顺序
Service → JUnit 5 + Mockito：断言业务分支、异常码、Mapper 调用副作用
构建层  → mvnw test（后端）/ vite build（前端）：作为提交前门禁
联调层  → 手工按 sql/schema.sql + sql/seed.sql 初始化后走主流程
```

### 2.2 为什么算法层能脱离数据库

算法输入是内存矩阵 `UserItemMatrix`（由 `behavior` 表数据构建，但构建过程在 Service 层完成），
策略类不持有任何 `Connection`/`Mapper`。因此相似度、召回、排序、兜底全部是可断言的纯函数。

> 这是相对参考项目最关键的改进：newbee-mall 的 `CoreMath` 直接查库，
> 导致「取前 3 个相似用户」这类逻辑错误无法被测试发现。

### 2.3 命名规范

被测方法_场景_预期结果，例如：

- `computeSimilarity_noCommonUsers_returnsZero`
- `recommendForUser_strategyThrows_degradesToHot`

## 6. 缺陷记录（本项目规避的参考项目缺陷及回归用例）

## 9. 结论

- 后端 90 个自动化用例全绿，覆盖算法核心、业务分支与鉴权入口，**编译与测试可作为提交门禁**。
- 前端可通过生产构建，但交互正确性依赖人工回归。
- 端到端联调风险集中在「数据库映射 + 前后端契约」，已在第 7 章显式登记，不假设其已通过。
