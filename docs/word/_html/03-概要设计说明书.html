2. 总体架构设计

2.1 架构风格

系统采用 B/S 前后端分离架构，后端为分层单体应用（Layered Monolith）， 前端为单页应用（SPA）。选择单体而非微服务的原因： 本项目为个人项目，业务边界清晰、部署运维成本敏感， 单体架构足以支撑需求且能显著降低复杂度，符合「合适优于时髦」的工程原则。

2.3 分层职责与依赖规则

层次 职责 依赖方向
Controller 接收 HTTP 请求、参数校验、调用 Service、封装响应 → Service
Service 业务逻辑编排、事务控制、权限校验、调用 Mapper 与推荐引擎 → Mapper
Recommend 推荐算法核心：相似度计算、召回、排序、兜底 → Mapper（只读）
Mapper 数据持久化，SQL 参数化，实体映射 → DB
Entity/DTO 数据载体，Entity 对应表，DTO 用于层间传输，VO 用于前端展示 无依赖

强制规则：

  • 禁止 Controller 直接调用 Mapper（无 Service 中转）。
  • 禁止 Service 反向依赖 Controller。
  • 禁止在 Controller 中编写业务逻辑。
  • 跨层数据一律使用 DTO/VO，禁止直接暴露 Entity 给前端。

4.2 推荐引擎设计（核心）

4.2.1 策略模式结构

        RecommendStrategy (接口)
         ├── recommend(userId, itemId, n) → List<ScoredItem>
         │
    ┌────┴─────┬──────────┬───────────┐
 UserCF     ItemCF    HotFallback  Hybrid
 Strategy   Strategy   Strategy    Strategy

引擎门面 `RecommendEngine` 根据场景路由到具体策略：

场景 使用策略
首页推荐 UserCF（失败降级 HotFallback）
详情页相似 ItemCF（失败降级同类目热门）
游客首页 HotFallback
猜你喜欢 Hybrid（UserCF 0.6 + ItemCF 0.4）

4.2.2 UserCF 算法流程

输入：目标用户 u，邻居数 K，推荐数 N
1. 加载全量有效行为，构建 用户→(商品→加权分) 映射
2. 对 u 与其余每个用户 v 计算余弦相似度：
       sim(u,v) = Σ(i∈Iuv) w(u,i)·w(v,i)
                  ───────────────────────
                  √Σ(i∈Iu)w(u,i)² · √Σ(i∈Iv)w(v,i)²
   其中 Iuv 为 u、v 共同交互过的商品集合，w 为行为加权分
3. 取 sim 最大的 K 个用户作为邻居集合 S(u,K)
4. 对候选商品 i（邻居交互过、u 未交互过、未下架）打分：
       score(u,i) = Σ(v∈S(u,K) ∩ N(i)) sim(u,v) · w(v,i)
   其中 N(i) 为对 i 有过行为的用户集合
5. 按 score 降序取 Top-N
6. 候选不足则用 HotFallback 补足

4.2.3 ItemCF 算法流程

输入：目标商品 i，推荐数 N
1. 构建 商品→(用户→加权分) 倒排索引
2. 计算物品 i 与物品 j 的余弦相似度（含热门惩罚）：
                    |N(i) ∩ N(j)|
       sim(i,j) = ─────────────────
                  √|N(i)| · |N(j)|
   热门惩罚：对 |N(i)| 过大的物品降低权重，避免热门物品与万物相似
3. 取 sim 最大的 Top-N 个商品（排除自身、已下架、用户已购）
4. 按相似度降序输出

4.2.4 冷启动策略

场景 策略
新用户（无行为） 返回近 30 天加权热门商品 Top-N
新商品（无行为） 返回同二级类目下热门商品
候选不足 用热门商品补足至 N 个
引擎异常 捕获异常、记录日志、降级返回热门商品，保证页面可用性

6. 接口设计规范

6.1 统一响应体

public class Result<T> {
    private int code;         // 0=成功，非0=错误码
    private String message;   // 提示信息
    private T data;           // 业务数据
    private long timestamp;   // 响应时间戳
}

6.2 错误码规范

区间 含义 示例
0 成功 `0 success`
1000–1999 通用错误 `1001 参数校验失败`
2000–2999 用户/认证 `2001 用户名或密码错误`
3000–3999 商品/类目 `3001 商品不存在`
4000–4999 交易 `4001 库存不足`
5000–5999 推荐 `5001 推荐服务降级`
9000–9999 系统错误 `9999 系统内部错误`

6.3 接口命名与路径规范

  • 路径统一前缀 `/api`。
  • 资源使用复数名词：`/api/products`、`/api/orders`。
  • 管理接口前缀 `/api/admin`。
  • 分页参数统一：`pageNum`（默认 1）、`pageSize`（默认 20）。
  • 时间字段统一使用 `LocalDateTime`，JSON 序列化格式 `yyyy-MM-dd HH:mm:ss`。

7. 非功能设计

7.1 性能设计

措施 说明
连接池 HikariCP，最大 20 连接，最小空闲 5
数据库索引 行为表 `(user_id)`、`(product_id)`、`(created_at)` 建索引
推荐结果缓存 首版不启用（数据量小，构建耗时毫秒级）；后续再做矩阵快照缓存，见 `docs/04` C2
行为异步写入 首版同步写入（数据量小、便于单测）；异步为后续优化，见 `docs/04` C3
分页 所有列表接口强制分页，禁止全表返回

7.2 安全设计

措施 说明
密码存储 BCrypt（strength=10）加盐哈希
认证 JWT（HS256，有效期 24 小时），请求头 `Authorization: Bearer <token>`
授权 基于角色的接口级鉴权，用户维度数据隔离（只能访问自身数据）
SQL 安全 MyBatis 全参数化 `#{}`，禁用 `${}`
配置安全 数据库口令走环境变量，仓库只提交 `.env.example`
越权防护 订单/购物车查询强制拼接当前用户 ID 作为过滤条件

7.3 可靠性设计

措施 说明
推荐降级 推荐引擎异常时自动降级为热门推荐，页面始终可用
事务 下单、库存扣减在同一事务内，库存更新加条件防超卖
全局异常处理 统一捕获异常，返回结构化错误，不暴露堆栈
日志 关键操作记录操作日志，异常记录错误日志

10. 迭代新增的架构组件（2026-10-30）

本轮迭代在原有「策略 + 引擎 + 编排服务」三层之上，新增四类横切组件：

组件 职责 关键决策
订单状态机 集中声明合法流转（`OrderStatus.nextStates`） 支付与确认收货不走通用改状态接口，堵住后台绕行
后台定时任务 超时取消（`OrderAutoCancelTask`）、超时确认收货（`OrderAutoReceiptTask`） `fixedDelay` 防堆叠；内部捕获异常防调度中断；阈值均可配置且 0 值关闭
推荐模型缓存 行为矩阵 + 用户相似邻居按矩阵版本号缓存 版本号随矩阵重建自增，缓存整体失效无需手动清理；TTL 300s，实测首页 367ms → 19ms
站内通知 支付/发货事件写入 `notification`，铃铛展示未读数 推送失败静默吞掉，绝不阻断主流程；接真实通道时只需在 push 内补发送动作

数据层相应增加 `order_status_log`（状态追溯）与 `notification` 两张表，orders 表增加 `pay_type / tracking_no / carrier / ship_time` 四列；演进方式见数据库设计说明书第 7 章。

推荐编排层新增两类后处理：多样性打散（同级类目配额，作用于首页与热门列表，刻意不作用于相似推荐）与冷启动分流（交互数低于阈值的新用户跳过协同过滤）。详见详细设计说明书第 15 章。
