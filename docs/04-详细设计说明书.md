概要设计成文在前，编码前做了三处收敛，本文以本文为准：

| 编号 | 概要设计 | 详细设计 | 理由 |
| ---- | -------- | -------- | ---- |

## 2. 设计总览

### 2.1 分层与调用规则

```
Controller ──▶ Service ──▶ Mapper ──▶ MySQL
                 │
                 ├──▶ RecommendEngine ──▶ 四个 Strategy （纯函数，不碰 DB）
                 └──▶ BehaviorService.buildMatrix() 提供算法输入
```

强制规则（违反即代码评审不通过）：

1. Controller 只做「收参数 → 调 Service → 包 Result」，不写 if/else 业务分支。
2. Service 不做 HTTP 相关处理（不碰 `HttpServletRequest`），当前用户 ID 用 `SecurityUtils` 取。
3. `recommend` 包**不注入 Mapper**，输入一律是 `UserItemMatrix`，保证纯函数、可单测。
4. 算法层的输出只有 `(itemId, score, reason)`，商品详情查询由 `RecommendService` 负责。

### 2.2 包结构

```
com.deng.recommend
├── RecommendApplication.java            启动类（@MapperScan）
├── common/        5 个：Result、ResultCode、BusinessException、GlobalExceptionHandler、PageResult
├── config/        6 个：SecurityConfig、CorsConfig、MybatisPlusConfig、OpenApiConfig、
│                        RecommendProperties、SecurityUtils
├── security/      4 个：UserPrincipal、JwtTokenProvider、UserDetailsServiceImpl、JwtAuthenticationFilter
├── controller/    9 个：Auth/Product/Category/Behavior/Recommend/Cart/Order/Review + admin/Admin
├── service/       9 个接口 + impl/ 9 个实现
├── recommend/     6 个策略/引擎 + similarity/1 + model/4 + evaluator/1
├── mapper/        8 个
├── entity/        8 个 + enums/3
├── dto/           8 个
└── vo/            8 个
```

### 2.3 全局编码约定

| 约定 | 规则 |
| ---- | ---- |
| 命名 | 类大驼峰；方法小驼峰；常量全大写；表字段小写下划线 |
| 时间 | 一律 `LocalDateTime`；JSON 输出格式 `yyyy-MM-dd HH:mm:ss` |
| 金额 | 一律 `BigDecimal`，禁止 `double/float` |
| 空值 | 集合方法返回空集合而不是 `null`；算法层必须能处理 `null` 入参 |
| 日志 | `@Slf4j`，异常用 `log.error("...", e)`；禁止 `printStackTrace()` |
| 事务 | 只加在 Service 的写方法上，`@Transactional(rollbackFor = Exception.class)` |
| 注入 | 只用构造器注入（`@RequiredArgsConstructor` + `final` 字段），禁止字段 `@Autowired` |
| 校验 | Jakarta Validation 注解写在 DTO 上，不写在 Entity 上 |
| 注释 | 只解释「为什么」，不复述「是什么」；每个类顶部一段职责说明 |

## 3. 通用层设计（`common`）

### 3.1 `Result<T>` 统一响应体

```java
public class Result<T> {
    private int code;
    private String message;
    private T data;
    private long timestamp;      // System.currentTimeMillis()

    public static <T> Result<T> success();
    public static <T> Result<T> success(T data);
    public static <T> Result<T> fail(ResultCode resultCode);
    public static <T> Result<T> fail(int code, String message);
}
```

约定：

- `code = 0` 成功，非 0 失败；**HTTP 状态码统一 200**，前端拦截器只看 `code`。
- `timestamp` 每次创建时写入，便于排查时序问题。

### 3.2 `ResultCode` 错误码枚举

```java
public enum ResultCode {
    SUCCESS(0, "成功"),
    PARAM_ERROR(1001, "参数校验失败"),
    UNAUTHORIZED(1002, "未登录或令牌无效"),
    FORBIDDEN(1003, "无权限访问"),
    RESOURCE_NOT_FOUND(1004, "资源不存在"),
    USERNAME_OR_PASSWORD_ERROR(2001, "用户名或密码错误"),
    USERNAME_EXISTS(2002, "用户名已被注册"),
    USER_DISABLED(2003, "账号已被禁用"),
    PASSWORD_MISMATCH(2004, "两次输入的密码不一致"),
    OLD_PASSWORD_ERROR(2005, "原密码错误"),
    PRODUCT_NOT_FOUND(3001, "商品不存在或已下架"),
    CATEGORY_NOT_FOUND(3002, "类目不存在"),
    STOCK_NOT_ENOUGH(4001, "库存不足"),
    ORDER_NOT_FOUND(4002, "订单不存在"),
    ORDER_STATUS_ILLEGAL(4003, "订单状态不允许该操作"),
    CART_EMPTY(4004, "购物车为空"),
    REVIEW_EXISTS(4005, "该商品已评价过"),
    RECOMMEND_ERROR(5001, "推荐服务不可用"),
    SYSTEM_ERROR(9999, "系统内部错误");

    private final int code;
    private final String message;
    // getter
}
```

> **为什么把错误码集中成枚举**：参考项目到处 `throw new RuntimeException("xxx")`，
> 前端只能靠字符串匹配，改一个字就断。错误码是接口契约的一部分。

### 3.3 `BusinessException`

```java
public class BusinessException extends RuntimeException {
    private final int code;

    public BusinessException(ResultCode resultCode);
    public BusinessException(ResultCode resultCode, String message);  // 覆盖默认提示
    public int getCode();
}
```

- 不填充堆栈信息可省性能，但本项目为学习项目，保留默认堆栈便于排查。
- 业务可预期错误一律抛它，**不要**抛 `RuntimeException`。

### 3.4 `GlobalExceptionHandler`（`@RestControllerAdvice`）

| 捕获异常 | 返回 code | 日志级别 | 说明 |
| -------- | --------- | -------- | ---- |
| `BusinessException` | 异常自带 | warn | 业务可预期，不打堆栈 |
| `MethodArgumentNotValidException` | 1001 | warn | 取第一个字段错误信息返回 |
| `BindException` | 1001 | warn | GET 查询参数绑定失败 |
| `ConstraintViolationException` | 1001 | warn | `@RequestParam` 上的校验 |
| `HttpRequestMethodNotSupportedException` | 1001 | warn | 方法不允许 |
| `AccessDeniedException` | 1003 | warn | 权限不足 |
| `AuthenticationException` | 1002 | warn | 未认证 |
| `Exception` | 9999 | **error** | 兜底，**绝不把堆栈返回前端** |

### 3.5 `PageResult<T>` 分页响应

```java
public class PageResult<T> {
    private long total;
    private int pageNum;
    private int pageSize;
    private long pages;
    private List<T> records;

    public static <T> PageResult<T> of(IPage<T> page);
    public static <T> PageResult<T> of(IPage<?> page, List<T> records); // 需要转换 VO 时用
}
```

> 第二个工厂方法很关键：`IPage<Product>` 要转成 `IPage<ProductVO>`，

## 4. 实体层与枚举（`entity`）

### 4.1 设计决策：枚举只存在于业务层

数据库里 `user.role`、`orders.status` 是 `TINYINT`，`behavior.behavior_type` 是 `VARCHAR`。
实体类**直接使用 `Integer` / `String` 存储编码**，在 Service 层用 `UserRole.of(code)` 转枚举。

> **为什么不用 MyBatis-Plus 的 `@EnumValue` / `IEnum`**：
> 它会把「数据库编码 ↔ 枚举」的映射藏进框架，初学时出问题很难定位；
> 显式在 Service 转一次，代码可读、可测，且 Entity 与表字段一一对应。

### 4.2 三个枚举

| 枚举 | 常量（编码, 含义） | 额外方法 |
| ---- | ------------------ | -------- |
| `UserRole` | `USER(1,"普通用户")`、`ADMIN(2,"管理员")` | `of(Integer code)` 未知值返回 `USER` |
| `BehaviorType` | `VIEW(1.0)`、`CLICK(2.0)`、`CART(3.0)`、`PURCHASE(5.0)`、`RATE(4.0)`（编码为字符串名） | `of(String code)` 未知值抛 `BusinessException(PARAM_ERROR)`；`getWeight()` |
| `OrderStatus` | `PENDING(0)`、`PAID(1)`、`SHIPPED(2)`、`COMPLETED(3)`、`CANCELLED(4)` | `of(Integer)`、`cancellable()`（仅 PENDING 为 true） |

`BehaviorType` 的权重是**推荐算法的核心输入**，必须固定：

```java
VIEW(     "VIEW",     1.0),   // 进入详情页
CLICK(    "CLICK",    2.0),   // 点击推荐位/列表
CART(     "CART",     3.0),   // 加购
PURCHASE( "PURCHASE", 5.0),   // 购买
RATE(     "RATE",     4.0);   // 评分
```

> 权重不能随机：参考项目用 `Math.random()` 伪造强度，导致同一份数据跑两次结果不同。
> 固定权重 + 确定性排序 = 可复现，这是能写单测的前提。

### 4.3 实体字段与映射

通用注解：`@Data`、`@TableName("表名")`、主键 `@TableId(type = IdType.AUTO)`。

| 实体 | 表 | 字段（Java 类型） | 特殊注解 |
| ---- | -- | ----------------- | -------- |
| `User` | `user` | id Long、username String、passwordHash String、nickname String、email String、avatar String、role Integer、status Integer、lastLoginTime LocalDateTime、isDeleted Integer、createTime LocalDateTime、updateTime LocalDateTime | `isDeleted` 加 `@TableLogic`；两个时间加 `@TableField(fill = ...)` |
| `Category` | `category` | id、name、parentId Long、sortOrder Integer、isDeleted、createTime、updateTime | 同上 |
| `Product` | `product` | id、categoryId Long、name、subtitle、mainImage、price BigDecimal、originalPrice BigDecimal、stock Integer、sales Integer、status Integer、description String、isDeleted、createTime、updateTime | 金额 `BigDecimal`，库存 `Integer` |
| `Behavior` | `behavior` | id、userId Long、productId Long、behaviorType String、weight BigDecimal、rating Integer、createdAt LocalDateTime | `createdAt` 列名 `created_at`，不加自动填充（由业务写入） |
| `Cart` | `cart` | id、userId、productId、quantity Integer、checked Integer、createTime、updateTime | `checked` 用 1/0 而非 Boolean，与表一致 |
| `Order` | `orders` | id、orderNo String、userId、totalAmount BigDecimal、status Integer、receiverName、receiverPhone、receiverAddr、paidTime、isDeleted、createTime、updateTime | `@TableName("orders")`，**避开关键字 order** |
| `OrderItem` | `order_item` | id、orderNo、productId、productName、price BigDecimal、quantity Integer、subtotal BigDecimal、createTime | 商品名/价格是**下单快照**，不随商品改价变化 |
| `Review` | `review` | id、userId、productId、orderNo、rating Integer、content、isDeleted、createTime、updateTime | 唯一键 `(user_id, product_id)` |

字段填充注解：

```java
@TableField(fill = FieldFill.INSERT)        private LocalDateTime createTime;
@TableField(fill = FieldFill.INSERT_UPDATE) private LocalDateTime updateTime;
@TableLogic                                  private Integer isDeleted;
```

`Behavior` 提供便捷方法（避免权重逻辑散落）：

```java
public void applyType(BehaviorType type) {
    this.behaviorType = type.getCode();
    this.weight = BigDecimal.valueOf(type.getWeight());
}
```

## 5. 配置层与安全层（`config` / `security`）

### 5.1 `RecommendProperties`（`@ConfigurationProperties(prefix = "recommend")`）

| 配置项 | 默认值 | 含义 |
| ------ | ------ | ---- |
| `default-top-n` | 10 | 未指定时的推荐数量 |
| `neighbor-k` | 20 | UserCF 邻居数 K |
| `popularity-penalty` | 0.0 | ItemCF 热门惩罚指数 α，0 表示不惩罚 |
| `user-cf-weight` | 0.6 | 混合推荐中 UserCF 权重 |
| `item-cf-weight` | 0.4 | 混合推荐中 ItemCF 权重 |
| `hot-days` | 30 | 热门统计时间窗口（天） |
| `max-behavior-rows` | 200000 | 单次构建矩阵最多加载的行为行数（保护内存） |

> **禁止**在算法类里出现 `3`、`0.6` 这类魔法数字；全部从这里取。

### 5.2 `MybatisPlusConfig`

1. `MybatisPlusInterceptor` + `PaginationInnerInterceptor(DbType.MYSQL)`：分页必须走插件，禁止手工拼 `LIMIT`。
2. `MetaObjectHandler`：insert 填 `createTime`、`updateTime`；update 填 `updateTime`。

### 5.3 `CorsConfig`

暴露 `CorsConfigurationSource` Bean：允许 `http://localhost:5173`，方法 `GET/POST/PUT/DELETE/OPTIONS`，
允许全部请求头，`allowCredentials(true)`，`maxAge(3600)`。

> 前端 Vite 默认 5173；`allowCredentials(true)` 时**不能用 `*`** 通配源，必须写具体源。

### 5.4 安全设计

#### 5.4.1 `UserPrincipal`（implements `UserDetails`）

| 字段/方法 | 说明 |
| --------- | ---- |
| `userId`、`username`、`role`（String，`USER`/`ADMIN`） | 登录主体信息 |
| `password` | 仅在登录校验时持有 BCrypt 哈希；JWT 过滤器构造的实例为 `null` |
| `getAuthorities()` | 返回 `ROLE_USER` / `ROLE_ADMIN` |
| `isEnabled()` | `status == 1` |

#### 5.4.2 `JwtTokenProvider`

| 方法 | 说明 |
| ---- | ---- |
| `generateToken(Long userId, String username, String role)` | subject=username，claim `uid`、`role`，HS256 签名 |
| `parseToken(String token)` | 解析并校验，失败抛 `JwtException` |
| `validateToken(String token)` | 布尔版，内部 catch 异常并 `log.debug` |
| `getUserId(String token)` / `getUsername(String token)` | 便捷读取 |

- 密钥来自 `security.jwt.secret`（环境变量 `JWT_SECRET`），**HS256 要求 ≥ 32 字节**，
  用 `Keys.hmacShaKeyFor(secret.getBytes(UTF_8))`。
- 有效期 `security.jwt.expiration`，默认 86400000 ms（24 小时）。

#### 5.4.3 `JwtAuthenticationFilter`（`OncePerRequestFilter`）

1. 读 `Authorization`，无 `Bearer ` 前缀 → 直接放行（由后续规则决定是否 401）。
2. `validateToken` 失败 → 放行（匿名），由 `AuthenticationEntryPoint` 返回 1002。
3. 成功 → 从 claims 构造 `UserPrincipal(userId, username, role)`，
   放入 `UsernamePasswordAuthenticationToken(principal, null, authorities)` 并写入 `SecurityContextHolder`。
4. **不查数据库**：JWT 无状态的代价是「禁用用户后旧令牌仍有效至过期」，
   这是已知限制，记录在案；如需即时生效，后续加令牌黑名单。

#### 5.4.4 `SecurityConfig` 授权规则

| 路径 | 规则 |
| ---- | ---- |
| `/api/auth/**` | permitAll |
| GET `/api/products/**`、`/api/categories/**`、`/api/reviews/**` | permitAll |
| GET `/api/recommend/hot`、`/api/recommend/similar/**` | permitAll |
| `/swagger-ui/**`、`/swagger-ui.html`、`/v3/api-docs/**` | permitAll |
| `/api/admin/**` | `hasRole("ADMIN")` |
| 其余（`/api/recommend/home`、`/api/behavior/**`、`/api/cart/**`、`/api/orders/**`、POST `/api/reviews`） | authenticated |

其他配置：`csrf.disable()`、`sessionCreationPolicy(STATELESS)`、注册 `cors`、
异常处理返回统一 JSON（HTTP 200 + code 1002/1003）、
`addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)`、
`BCryptPasswordEncoder(10)`。

#### 5.4.5 `SecurityUtils`

```java
public static Long getCurrentUserId();   // 从 SecurityContext 取 UserPrincipal.userId
public static Long getCurrentUserIdOrNull(); // 游客场景返回 null
```

取不到用户时抛 `BusinessException(UNAUTHORIZED)`。
所有用户维度查询（购物车、订单）必须用它的返回值过滤，**禁止信任前端传的 userId**。

#### 5.4.6 登录流程（配合 `UserDetailsServiceImpl`）

```
POST /api/auth/login
  → AuthServiceImpl.login
      1. userDetailsService.loadUserByUsername(username)
         └ UsernameNotFoundException → 2001（与密码错误同一提示，防账号枚举）
      2. passwordEncoder.matches(rawPassword, principal.getPassword())
         └ false → 2001
      3. principal.isEnabled() == false → 2003
      4. 更新 user.last_login_time
      5. jwtTokenProvider.generateToken(...)
      6. 返回 UserVO（含 token，绝不含 passwordHash）
```

`UserDetailsServiceImpl.loadUserByUsername`：按用户名查 `user` 表（逻辑删除自动过滤），
不存在抛 `UsernameNotFoundException`，存在则装配 `UserPrincipal`。

## 6. 数据访问层设计（`mapper`）

8 个 Mapper 全部 `extends BaseMapper<实体>`，加 `@Mapper`。除 `BehaviorMapper` 外不写自定义 SQL：
单表 CRUD 与条件查询交给 `LambdaQueryWrapper` / `LambdaUpdateWrapper`。

### 6.1 `BehaviorMapper` 自定义方法（推荐算法唯一的数据入口）

```java
@Select({
    "<script>",
    "SELECT user_id, product_id, weight, created_at FROM behavior",
    "WHERE 1 = 1",
    "<if test='since != null'> AND created_at &gt;= #{since} </if>",
    "ORDER BY created_at DESC",
    "LIMIT #{limit}",
    "</script>"
})
@Results({
    @Result(property = "userId",     column = "user_id"),
    @Result(property = "productId",  column = "product_id"),
    @Result(property = "weight",     column = "weight"),
    @Result(property = "occurredAt", column = "created_at")
})
List<BehaviorRecord> selectBehaviorRecords(@Param("since") LocalDateTime since,
                                           @Param("limit") int limit);
```

> 三个要点：
> 1. 参数一律 `#{}`，禁止 `${}`（AGENTS.md 硬性要求）。
> 2. `<` 在 XML 中要转义成 `&gt;=`，否则 MyBatis 解析报错。
> 3. 直接映射成算法模型 `BehaviorRecord`，让 Entity 不进入算法层。

### 6.2 其它 Mapper 的使用约定

| Mapper | 典型用法 |
| ------ | -------- |
| `UserMapper` | 按用户名查重、登录查询、后台分页 |
| `ProductMapper` | 详情、分页搜索、批量 `selectBatchIds`、条件扣库存 |
| `CategoryMapper` | 全量查询后在内存组树（两级，量小不值得递归查库） |
| `CartMapper` | 按 `(userId, productId)` 查、按 userId 列、按勾选删除 |
| `OrderMapper` | 按 `orderNo` 查、按 userId + status 分页 |
| `OrderItemMapper` | 按 `orderNo` 批量查 |
| `ReviewMapper` | 按 productId 分页、按 `(userId, productId)` 查重 |

## 7. 推荐引擎详细设计（`recommend`）★核心

### 7.1 类职责

| 类 | 职责 | 依赖 |
| -- | ---- | ---- |
| `RecommendStrategy` | 策略接口：`getName()`、`recommend(UserItemMatrix, RecommendRequest)` | 无 |
| `UserCFStrategy` | 基于用户的协同过滤 | `RecommendProperties` |
| `ItemCFStrategy` | 基于物品的协同过滤（含热门惩罚） | `RecommendProperties` |
| `HotFallbackStrategy` | 按热度排序的热门兜底 | `RecommendProperties` |
| `HybridStrategy` | UserCF + ItemCF 归一化加权融合 | 两个策略 + `RecommendProperties` |
| `RecommendEngine` | 门面：路由、补全、异常降级 | 四个策略 + `RecommendProperties` |
| `CosineSimilarity` | 余弦相似度、L2 范数、带惩罚相似度 | 无（静态工具类，私有构造） |
| `UserItemMatrix` | 双索引矩阵 + 热度 | 无 |
| `BehaviorRecord` | 算法输入单元 `(userId, productId, weight, occurredAt)` | 无 |
| `ScoredItem` | 算法输出单元 `(itemId, score, reason)`，`Comparable` | 无 |
| `RecommendRequest` | 请求上下文（userId、itemId、topN、neighborK、excludeItemIds） | 无 |
| `RecommendEvaluator` | 离线评测：切分、指标计算 | 无 |

**算法包永不注入 Mapper/Service**——它是纯 Java，可以被 JUnit 直接 new 出来测。

### 7.2 `UserItemMatrix` 数据结构

```java
Map<Long, Map<Long, Double>> userItems;      // 正向：用户 → (商品 → 加权分)
Map<Long, Map<Long, Double>> itemUsers;      // 倒排：商品 → (用户 → 加权分)
Map<Long, Double> itemPopularity;            // 商品热度 = 全站行为权重之和
```

构建规则（`build(List<BehaviorRecord>)`）：

1. `records == null || isEmpty()` → 返回空矩阵（**不是 null**）。
2. 跳过 `userId` 或 `productId` 为 null 的记录。
3. `weight == null` 视为 0；`weight <= 0` 跳过。
4. 同一用户对同一商品多次行为：正向与倒排索引都用 `merge(..., Double::sum)` **累加**；
   热度同步累加。
5. 提供 `getUserItems` / `getItemUsers`（无数据返回 `Collections.emptyMap()`）、
   `getPopularity`（无数据返回 0.0）、`hasInteraction`、`allUserIds`、`allItemIds`、
   `userCount`、`itemCount`、`isEmpty`。

> **为什么同时维护两个索引**：UserCF 按用户取向量，ItemCF 按物品取向量。
> 只建一个索引，另一个算法每次都要扫描全表重建，O(B) 变 O(U·B)。
> 累加而不是取最大值：多次浏览、先浏览后购买，就是更强的兴趣信号。

### 7.3 余弦相似度 `CosineSimilarity`

```
              Σ(i∈A∩B) wA(i) · wB(i)
sim(A,B) = ─────────────────────────────
             √Σ(i∈A)wA(i)² · √Σ(i∈B)wB(i)²
```

实现要点：

| 要点 | 规则 |
| ---- | ---- |
| 空值/空向量 | 返回 `0.0`（**绝不返回 NaN**） |
| 无交集 | 点积为 0 → 返回 `0.0`（提前返回，省一次开方） |
| 遍历优化 | 遍历较短向量，在长向量里查 key |
| 除零 | 任一范数为 0 → 返回 `0.0` |
| 浮点越界 | 结果 `Math.max(0.0, Math.min(1.0, sim))` 收敛到 [0,1] |
| 热门惩罚 | `computeWithPenalty(a, b, alpha)`：`sim / \|b\|^alpha`，`alpha <= 0` 或 `\|b\| <= 1` 时原样返回 |

> **为什么不用皮尔森**：参考项目皮尔森在共同评分人数 n=0 时返回 `NaN`，
> 而 `NaN == 0` 为 `false`，导致除零判断失效、排序出现诡异结果。
> 余弦没有「减去均值」的除法，天然规避这个坑，且 [0,1] 区间好解释。

### 7.4 `UserCFStrategy` 流程

```
输入：userId、topN（默认取配置）、neighborK（默认取配置）、excludeItemIds
1. userId 为空 或 矩阵空 → 返回空列表
2. 目标用户无历史行为 → 返回空列表（由 Engine 走热门兜底，不在这里 NPE）
3. 遍历全部其他用户，算 sim(目标用户, 其他用户)，sim > 0 才保留
4. 按 sim 降序排（ScoredItem 自然序），取前 K 个邻居
5. 对每个邻居的每个商品：
     - 目标用户已交互过的 → 跳过
     - score += sim × 邻居对该商品的加权分
6. 按 score 降序取 Top-N，reason = "与您兴趣相似的 K 位用户也在关注"
```

边界：

| 场景 | 行为 |
| ---- | ---- |
| 无其他用户相似度 > 0 | 返回空列表 → Engine 补热门 |
| `neighborK <= 0` | 用配置值 |
| `topN <= 0` | 用配置值 |
| `excludeItemIds` 为 null | 视为空集合 |

复杂度：`O(U × I_u × I_v)`，U 为用户数、I 为平均交互数；结果打分 `O(K × I_v)`。

### 7.5 `ItemCFStrategy` 流程

```
输入：itemId、topN、excludeItemIds
1. itemId 为空 或 矩阵空 → 返回空列表
2. 目标商品无受众（无共现数据）→ 返回空列表（由 Engine/Service 降级）
3. 遍历全部其他商品，用倒排向量算带惩罚相似度
4. 按相似度降序取 Top-N，reason = "关注该商品的用户也关注了此商品"
5. 排除目标商品自身与 excludeItemIds
```

热门惩罚：`sim / |受众|^α`。α 取 `recommend.popularity-penalty`，
默认 0（不惩罚）。α 增大可抑制「热门商品与万物相似」，
调参后需用评测器的 Coverage / AvgPopularity 验证。

复杂度：`O(I × U_i × U_j)`。

### 7.6 `HotFallbackStrategy` 流程

1. 矩阵空 → 空列表。
2. 遍历全部商品，`score = matrix.getPopularity(itemId)`，`score > 0` 才保留。
3. 过滤 `excludeItemIds`，按 score 降序取 Top-N，`reason = "近期热门商品"`。

「近 30 天热门」由调用方传入用近 30 天行为构建的矩阵实现，策略本身不关心时间窗口。

### 7.7 `HybridStrategy` 流程

两个策略分数域不同（UserCF 是加权得分，ItemCF 是相似度），**不能直接相加**：

```
归一化：norm(score) = score / max(score of that strategy)
融合：  score(i) = 0.6 × norm(userCf(i)) + 0.4 × norm(itemCf(i))
```

规则：

| 场景 | 行为 |
| ---- | ---- |
| `userId` 为空 | 跳过 UserCF |
| `itemId` 为空 | 跳过 ItemCF |
| 两路都空 | 返回空列表 |
| 某路 maxScore ≤ 0 或权重 ≤ 0 | 跳过该路（避免除零） |

结果重新按分数降序排，`reason = "综合您的浏览与购买偏好推荐"`。

### 7.8 `RecommendEngine` 门面

对外四个方法：

```java
List<ScoredItem> recommendForUser(UserItemMatrix m, Long userId, int topN, List<Long> exclude);
List<ScoredItem> recommendSimilar(UserItemMatrix m, Long itemId, int topN, List<Long> exclude);
List<ScoredItem> recommendHot(UserItemMatrix m, int topN, List<Long> exclude);
List<ScoredItem> recommendHybrid(UserItemMatrix m, Long userId, Long itemId, int topN, List<Long> exclude);
```

内部统一走 `executeWithFallback(matrix, request, scenario, supplier, allowSupplement)`：

```
try   result = supplier.get()                 // 调具体策略
catch 任意异常 → log.error("[scenario] 推荐计算异常", e); result = 空列表
if result == null → 空列表
if !allowSupplement 或 result.size() >= topN → 直接返回
补全：
  fallbackRequest.topN = topN - result.size()
  fallbackRequest.excludeItemIds = 已推荐 ID ∪ 原 exclude
  try 热门策略补足，异常 → log.error 后返回原结果
  用 LinkedHashSet 合并去重（ScoredItem 是 @Data，按值去重）
```

| 场景 | 策略 | 补全 |
| ---- | ---- | ---- |
| 首页推荐 | UserCF | 是 |
| 详情页相似 | ItemCF | 是 |
| 游客/冷启动 | HotFallback | 否（自身就是兜底） |
| 猜你喜欢 | Hybrid | 是 |

> **降级的哲学**：推荐是增强功能，不是核心交易链路。
> 算法抛异常必须返回「热门商品」而不是 500，否则一个相似度 bug 会把整个首页搞挂。

### 7.9 冷启动矩阵

| 场景 | 处理位置 | 做法 |
| ---- | -------- | ---- |
| 新用户无行为 | `UserCFStrategy` 返回空 → Engine 补全 | 热门 Top-N |
| 新商品无受众 | `ItemCFStrategy` 返回空 → Engine 补全 | 热门 Top-N（同类目热门属增强项，v1 不做） |
| 矩阵为空（全站无行为） | 各策略返回空 | Service 返回空列表，前端展示「暂无推荐」 |
| 引擎异常 | Engine catch | 热门兜底，页面始终可用 |

### 7.10 `RecommendEvaluator` 离线评测

接口：

```java
@FunctionalInterface
interface Recommender { List<ScoredItem> recommend(Long userId, int topN); }

static EvaluationResult evaluate(List<BehaviorRecord> train, List<BehaviorRecord> test,
                                 Recommender recommender, int topN);
static List<BehaviorRecord>[] splitByTime(List<BehaviorRecord> records, double trainRatio);
```

流程：

1. 用训练集构建矩阵（`trainMatrix`）。
2. 测试集按用户聚合真实正样本 `T(u)`（去重）。
3. 物品全集 `I = 训练集物品 ∪ 测试集物品`（覆盖率分母）。
4. 对每个有测试正样本的用户 `u` 调推荐器，得 `R(u)`：
   - `hit = |R(u) ∩ T(u)|`
   - `Precision(u) = hit / |R(u)|`（除以**实际推荐数**，而非固定 N，避免不满 N 时失真）
   - `Recall(u) = hit / |T(u)|`
5. 指标：

| 指标 | 公式 |
| ---- | ---- |
| Precision@N | `(1/\|U\|) Σ Precision(u)` |
| Recall@N | `(1/\|U\|) Σ Recall(u)` |
| F1 | `2PR / (P + R)`，`P + R == 0` 时取 0 |
| Coverage | `\|∪R(u)\| / \|I\|` |
| AvgPopularity | `(1/Σ\|R(u)\|) Σ ln(1 + popularity(i))`，越小越能挖长尾 |

6. `splitByTime`：按 `occurredAt` 升序（null 排最前），
   前 `floor(size × trainRatio)` 条为训练集，其余为测试集；默认 0.8。

> **评测必须按时间切分**，不能随机切：随机切会让「未来行为」泄漏进训练集，
> 指标虚高。这是推荐系统评测最常见的自欺欺人。

### 7.11 性能与容量边界

| 环节 | 复杂度 | 说明 |
| ---- | ------ | ---- |
| 矩阵构建 | `O(B)` | B 为行为条数，上限 `max-behavior-rows` |
| UserCF | `O(U² · I)` | 用户量是瓶颈；本项目单机数据量（千级用户）可接受 |
| ItemCF | `O(I² · U)` | 商品量是瓶颈 |
| 内存 | `O(B)` | 双索引各存一份 (user,item,weight) |

若数据量增长到十万级用户/商品，再引入离线预计算相似度矩阵，而不是现在做。

### 8.4 `BehaviorService`

```java

```

report 规则：

1. `BehaviorType.of(code)` 失败 → `PARAM_ERROR`。
2. 商品不存在 → `PRODUCT_NOT_FOUND`（防止脏数据污染矩阵）。
3. `RATE` 必须带 1–5 的 rating，否则 `PARAM_ERROR`。
4. `behavior.applyType(type)` 自动填 `behaviorType` 与 `weight`，`createdAt = now()`。

> 需求里「重复浏览更新权重而非无限累加」与算法层「同用户同商品累加」存在张力：
> v1 明确选择**累加**（矩阵侧），因为累加能表达「反复浏览 = 强兴趣」；
> 若后续要做防刷，在 report 处按「同 type 同商品当天已存在则不再写入」去重。

`buildMatrix` 调 `behaviorMapper.selectBehaviorRecords(since, maxBehaviorRows)` 后
`UserItemMatrix.build(...)`。

### 8.5 `RecommendService`

```java
List<RecommendVO> recommendForUser(Long userId, int topN);
List<RecommendVO> recommendSimilar(Long itemId, int topN);

```

编排职责（算法不查库，所以这些都在 Service）：

| 步骤 | 做法 |
| ---- | ---- |
| 归一化 topN | `topN <= 0` → 配置默认值 |
| 构建矩阵 | `behaviorService.buildMatrix(since)`；热门用「近 hotDays 天」，其余用全量 |
| 排除列表 | 已下架商品 + 该用户已购买商品（`behavior_type = PURCHASE`） |
| 算法调用 | 只调 `RecommendEngine` 的四个方法 |
| 转 VO | `selectBatchIds(ids)` 批量查商品 → `ProductVO.from` → `RecommendVO.of(product, item)` |
| 保序 | **按 `ScoredItem` 的顺序遍历**组装，不要按商品 ID 排序 |
| 过滤 | 商品不存在或 `status != 1` 的直接跳过 |

`evaluate`：取全量行为 → 少于 10 条返回空结果并 `log.warn` →
`splitByTime(0.8)` → 用训练集矩阵构造 `Recommender` 调评测器。

### 8.7 `OrderService`

```java
OrderVO create(Long userId, OrderCreateRequest request);          // @Transactional
PageResult<OrderVO> page(Long userId, Integer status, int pageNum, int pageSize);
OrderVO detail(Long userId, String orderNo);
void cancel(Long userId, String orderNo);                          // @Transactional
```

`create` 事务内步骤（任一步失败整体回滚）：

1. 查当前用户 `checked = 1` 的购物车项；为空 → `CART_EMPTY`。
2. 逐项校验商品存在且 `status = 1`；否则 `PRODUCT_NOT_FOUND`。
3. 扣库存（**条件更新防超卖**）：
   `UPDATE product SET stock = stock - #{qty} WHERE id = #{id} AND stock >= #{qty}`，
   影响行数 0 → `STOCK_NOT_ENOUGH`。
4. 以数据库当前价计算 `subtotal` 与 `totalAmount`（不信任前端价格）。
5. 生成订单号：`yyyyMMddHHmmss` + 6 位随机数。
6. 插入 `orders`，再插 `order_item`（商品名、单价做快照）。
7. 记录 `PURCHASE` 行为（走 `BehaviorService.report`，保证权重逻辑唯一）。
8. 物理删除已下单的购物车项（购物车是临时数据，表无逻辑删除字段）。
9. 返回 `OrderVO`（含明细）。

`cancel`：只能取消 `PENDING`（`OrderStatus.cancellable()`），否则 `ORDER_STATUS_ILLEGAL`；
状态改 `CANCELLED`，逐项回滚库存。

`page/detail` 必须拼 `userId` 过滤（传别人的 orderNo 也查不到）。

## 10. 关键时序

### 10.1 行为上报 → 推荐生效

```
前端(详情页/加购/下单/评价)
  → POST /api/behavior/report（JWT）
  → BehaviorController
  → BehaviorService.report
       ├ 校验商品存在
       ├ applyType 填 weight
       └ insert behavior
  → 返回 Result.success()

下次 GET /api/recommend/home
  → RecommendService.recommendForUser
       ├ BehaviorService.buildMatrix(null)      ← 读 behavior 表
       ├ RecommendEngine.recommendForUser       ← UserCF + 热门补全
       └ 批量查商品 → List<RecommendVO>
```

> 行为表是整条链路的**唯一数据源**。这就是参考项目缺 behavior 表、
> 只能从订单反推、冷启动无解的根本原因。

### 10.2 下单

```
POST /api/orders
  → @Transactional
      1 查勾选购物车（空 → 4004）
      2 校验商品上架
      3 条件 UPDATE 扣库存（0 行 → 4001 回滚）
      4 计算金额（DB 价格）
      5 insert orders
      6 insert order_item（快照）
      7 BehaviorService.report(PURCHASE)
      8 delete 已下单购物车项
  → 返回 OrderVO
异常：任意步骤抛 BusinessException → 事务整体回滚
```

### 10.3 离线评测

```
POST /api/admin/orders? ... 不，是 POST /api/recommend/evaluate
  → RecommendService.evaluate
       ├ selectBehaviorRecords(null, maxRows)
       ├ size < 10 → warn + 空结果
       ├ splitByTime(0.8)
       └ RecommendEvaluator.evaluate(train, test, recommender, topN)
  → 返回 Precision/Recall/F1/Coverage/AvgPopularity
```

## 14. 设计约束回顾

| 约束 | 落地方式 |
| ---- | -------- |
| 算法纯 Java、不引 ML 框架 | `recommend` 包只有 JDK 集合类与 Lombok |
| 算法可单测 | 输入 `UserItemMatrix`，不注入 Mapper |
| 无魔法数字 | 全部进 `RecommendProperties` |
| 无硬编码口令 | `application.yml` 用 `${DB_PASSWORD:}`，密钥用 `${JWT_SECRET:...}` |
| 全参数化 SQL | Mapper 只用 `#{}`，`LambdaQueryWrapper` |
| 密码 BCrypt | `BCryptPasswordEncoder(10)`，字段名 `passwordHash` |
| 越权防护 | `SecurityUtils.getCurrentUserId()` + 查询强制拼 userId |
| 事务 | 下单/取消/注册/评价加 `@Transactional(rollbackFor = Exception.class)` |
| 推荐可降级 | 引擎 catch 全部异常 → 热门兜底 |
