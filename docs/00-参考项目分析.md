## 2. 模块实现分析

### 2.1 分层结构

原项目采用经典的**三层架构**（表现层 / 持久层 / 实体层）：

```
src/
├── view/       LoginFrame / SignFrame / TenantFrame      —— 公共界面（登录注册）
├── Adminview/  AdminFrame + 6 个管理功能 Frame           —— 管理员端界面
├── Tenantview/ ApartmentFrame / Contract / Malfunction   —— 租客端界面
├── Dao/        BaseDao + 9 个业务 Dao                    —— JDBC 数据访问
├── model/      User / Tenant / Staff / Apartment ...     —— 实体 POJO
├── util/       DButil / Strutil / Dateutil               —— 工具
└── images/     46 个图标资源
```

**继承了什么（值得保留）**

- 清晰的包级职责划分：`model` / `Dao` / `view` 三者分离，这是正确的方向。
- `BaseDao` 抽象父类抽取公共的 `Connection` 与 `close()`，体现了复用意识。
- 使用 `PreparedStatement` 而非 `Statement`，具备基本的防注入意识。
- 用枚举 `UserType`（租客/员工/超级管理者）表达角色，比魔法字符串好。
- 大量使用 DTO 式的实体对象在层间传递数据。

### 2.2 各模块实现细节

#### （1）数据库连接模块 `util/DButil.java`

```java
private static String jdbcDriver = "com.mysql.jdbc.Driver";

public static Connection getConnection() {
    Class.forName(jdbcDriver);
    return DriverManager.getConnection(
        "jdbc:mysql://localhost:3306/houselease?serverTimezone=GMT%2B8&characterEncoding=UTF-8",
        "root", "123456");   // ← 硬编码口令
}
```

- 每次调用 `DriverManager.getConnection()` 新建一条物理连接，**没有连接池**。
- 使用的是**已废弃的驱动类名** `com.mysql.jdbc.Driver`（MySQL 8 正确写法为 `com.mysql.cj.jdbc.Driver`）。
- 连接串、账号、口令全部硬编码在源码里。

#### （2）数据访问基类 `Dao/BaseDao.java`

```java
public abstract class BaseDao {
    protected Connection con = DButil.getConnection();   // ← 实例化即建连接
    protected PreparedStatement pStatement = null;

    protected void close() {
        this.con.close();      // ← 只关 Connection
    }
}
```

**这是全项目最严重的设计缺陷：**

- `con` 是**实例字段**且在构造时就建立连接。这意味着 `new UserDao()` 一次就开一条连接。
- `close()` 只关闭 `Connection`，**从不关闭 `PreparedStatement` 和 `ResultSet`**，
  造成语句句柄与结果集资源泄漏。
- 一次 `close()` 之后，这个 Dao 实例的 `con` 就失效了，但代码里到处都在复用同一个 Dao 对象，
  导致「连接已关闭」异常随时可能爆发。
- 各子类为了绕过这个问题，不得不手动 `this.con = DButil.getConnection();` 重新建连接
  （`MalfunctionDao` 里每个方法开头都这么干），说明设计本身已经失控。

#### （3）数据访问实现 `Dao/*.java`

以 `ApartmentDao.queryApartment()` 为例：

```java
String sqlStr = "select * from apartment where tNo like '%"+apartment.gettNo()+"%' "
              + "and aNo like '%"+apartment.getaNo()+"%' "
              + "and aSite like '%"+apartment.getSite()+"%' ";
this.pStatement = this.con.prepareStatement(sqlStr);   // ← 拼接后再预编译
```

- 名义上用了 `PreparedStatement`，实际**先把用户输入拼进 SQL 再预编译**，
  注入防护形同虚设。`MalfunctionDao.AlterMalfunction()` 的 `WHERE mNo='"+...+"'` 同样如此。
- 结果集一律用**列下标**取值 `executeQuery.getString(1)`，一旦表结构加列就全盘错位。
- 返回值用**字符串 `"true"` / `"false"`** 表示成败（`addMalfunctionInfo` 返回 `String flag`），
  而不是 `boolean` 或抛出异常。
- 异常只做 `e.printStackTrace()`，吞掉错误后返回失败标志，调用方无法感知真实原因。
- **没有事务**：新增合同、修改房源这类需要多表一致性的操作完全没有事务保护。

#### （4）实体层 `model/*.java`

- 标准 POJO + getter/setter，符合 JavaBean 规范。
- 但存在真实 Bug：`UserType` 枚举的构造器**漏赋值 `index`**——

  ```java
  private UserType(String name, int index) {
      this.name = name;
      // this.index = index;  ← 遗漏，index 永远是 0
  }
  ```

- 实体字段用 `String` 存日期（`mBudgetDate`、`mWorkDate`），而非 `LocalDate`。

#### （5）界面层 `view/` `Adminview/` `Tenantview/`

- 由 Eclipse WindowBuilder 生成，大量 `setBounds(x, y, w, h)` **绝对定位**硬编码坐标。
- 界面类与业务逻辑高度耦合，例如 `LoginFrame.comfirmButton()` 里直接：

  ```java
  TenantDao tenantDao = new TenantDao();          // 界面直接 new Dao
  Tenant tenant = tenantDao.LoginIn(uNo, uPassword);
  if (tenant == null) { JOptionPane.showMessageDialog(this, "用户名密码错误"); return; }
  new TenantFrame(userType, tenant).setVisible(true);
  ```

  —— 登录鉴权、错误处理、页面跳转全部塞在一个按钮的监听器里，无法单测、无法复用。
- 每个功能一个 `JFrame`，通过 `new XxxFrame().setVisible(true)` + `this.dispose()` 切换，
  窗口实例不受控，容易残留僵尸窗口。

#### （6）工具层 `util/`

- `Strutil.notEmpty()`：语义与命名相反（方法叫 notEmpty，空时返回 false），可读性差。
- `Dateutil.DateToSqlDate()`：用 `SimpleDateFormat` 格式化日期（该类非线程安全）。

### 2.3 安全机制

| 安全项       | 实现情况                                                       |
| ------------ | -------------------------------------------------------------- |
| 身份认证     | 仅按账号+密码查库比对，无会话管理、无 Token                    |
| 密码存储     | **明文存储**，SQL 直接 `where bNo=? and bPassword=?` 比对      |
| 权限控制     | 依赖下拉框选择的角色，切换页面不做二次校验，可越权             |
| SQL 注入     | 部分接口存在字符串拼接，存在注入风险                           |
| 输入校验     | 基本缺失，仅 `Strutil.notEmpty()` 判空                         |
| 敏感配置     | 数据库账号口令硬编码在源码                                     |

## 5. 对新项目的指导结论

### 5.1 应当继承的优点

1. **分层意识**：`model` / `Dao` / `view` 分离的方向是正确的，新项目在此基础上补上缺失的
   **Service 层**，形成 Controller → Service → Mapper → DB 四层。
2. **基类抽取**：`BaseDao` 抽取公共数据库操作的思路正确，只是实现错了。
   新项目用 MyBatis-Plus 的 `ServiceImpl<M, T>` 与 `BaseMapper<T>` 达成同样的复用，
   且由框架正确管理连接生命周期。
3. **枚举表达角色**：`UserType` 的设计思路保留，新项目用 `UserRole` 枚举 + 数据库字典表。
4. **DTO 传参**：实体对象在层间传递的习惯保留，新项目进一步区分
   `Entity`（持久层）/ `DTO`（传输层）/ `VO`（视图层）。

### 5.2 必须升级的方向

| 维度       | 从                   | 到                                             |
| ---------- | -------------------- | ---------------------------------------------- |
| 架构形态   | C/S 单机桌面         | B/S 前后端分离，浏览器访问                     |
| 后端框架   | 裸 JDBC              | Spring Boot 3 + MyBatis-Plus                   |
| 连接管理   | 每次新建物理连接     | HikariCP 连接池                                |
| 界面       | Swing 绝对定位       | Vue 3 + Element Plus 响应式                    |
| 构建       | Eclipse 手工配 jar   | Maven + Wrapper，`pom.xml` 声明依赖            |
| 鉴权       | 明文比对             | BCrypt + JWT + Spring Security                 |
| 数据访问   | 手写 SQL + 列下标    | MyBatis 参数化 + 自动映射                      |
| 事务       | 无                   | `@Transactional`                               |
| 质量保障   | 无测试               | JUnit 5 + Mockito，交付前全量通过              |
| 配置       | 硬编码               | `application.yml` + 环境变量                   |
| 日志       | printStackTrace      | Slf4j + Logback + 全局异常处理                 |
| 版本管理   | 无                   | Git + Conventional Commits + GitHub            |

### 5.3 新增能力（原项目完全没有）

- **推荐引擎**：UserCF（基于用户协同过滤）+ ItemCF（基于物品协同过滤）双引擎，
  余弦相似度 + Top-K 邻居截断，热门商品兜底冷启动。
- **RESTful API**：统一的 `Result<T>` 响应体、全局异常处理、参数校验。
- **API 文档**：SpringDoc OpenAPI（Swagger UI）自动生成接口文档。
- **容器化**：Dockerfile + docker-compose 一键启动。
- **工程文档**：可行性分析、需求规格、概要设计、详细设计、数据库设计、
  测试计划与报告、部署手册、用户手册。
- **CI 就绪**：Maven 标准目录结构，可直接接入 GitHub Actions。
